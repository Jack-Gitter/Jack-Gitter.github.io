What is CQRS?

CQRS, also known as command query response segregation, is a way to functionally separate the reads and writes of an application. CQRS, in practice, involves separating out the write model from the read model, as typically the data you need to maintain consistency and uphold invariants is not always the same exact data as you want to read. Throughout this article, I will be using DDD nomenclature to reference core programming concepts and ideas, however CQRS is not inherently tied to DDD in any way. CQRS is much simpler than issues revolving around scalability, CDC, or any other topics that it is usually developed in tandem with, however it enables these performacne enhancements and architecture decisions

For those unfamiliar, a "command" within CQRS is essentially anything that will change the underlying data, think POST, PATCH, PUT requests. For queries, think anything that reads data without modification, for example GET requests

Why CQRS

With respect to DDD, CQRS allows for the separation of aggregate roots from the data models which are queried and displayed in the application. Aggregate roots typically fetch complex data from a database with locking, in order to uhold invariants about some data. Because reading data does not in any way change the state of the database, it is therefore safe to break out of these aggregate roots (whose purpose is to uphold invariants) and fetch data only the UI would care about. This is extremely helpful when the data required in the UI differes in any significant way from what data is fetched for the aggregate, allowing for optimization of SQL queries for hot read paths.

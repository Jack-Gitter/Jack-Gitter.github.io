What is CQRS?

CQRS, also known as command query response segregation, is a way to separate the models used for writing data and reading data. Within CQRS, a command is a request which updates data, think POST, PATCH, PUT, etc. A query is a request just to fetch data, think GET.

What CQRS is not

CQRS is not the same as DDD, does not require a separate read database, and does not require the use of domain events, eventual consistency, or CDC. At its heart, it is purely concerned with the separation of models for reading and writing, however it enabled and is often talked about in the same context as DDD and scalability/performance. Another benefit is code simplicity and separation of concerns, keeping code quality high and repositories organized.

Why CQRS

Although I did explicitly say that CQRS does not require the use of DDD in order to be considered CQRS, in my opinion, the strongest benefit of CQRS comes when utilizing data modeling concepts found in DDD, such as aggregates. An aggregates main purpose is to protect business invariants and ensure that data remains consistent. As such, aggregates often have to encompass many smaller entities in order to protect the rules of the business. Quite often the data required for UI pages does not encompass all of the data in the aggregate, and in some cases could even require data outside the bounds of any one specific aggregate. As such, it could become cumbersome to attempt to utilize the aggregate data model to fetch data, especially when no invariants need to be upheld for read operations. Because read operations do not udpate any data and therefore cannot violate any invaraints, SQL queries can be fine tuned and optimized to fetch exactly the data required by the UI without having to worry about upholding business rules. At its most simplest, this can just be implemented with a raw SQL query, selecting and joining any columns from within the same database. This is CQRS at its most pure form, and often times it is enough in order to achieve great separation of concerns and performance increases!

What is this post about?

This post is taking CQRS to the most extreme, complex, and scalable way that I could think of. It is in no way what should be strived for out of the gate, and is most likely only necessary with extremely hot read paths for thousands of requests a second. Starting with the aformentioned strategy of simply separating DDD aggregate roots for writes and raw sql queries for reads is a great starting point for implementing CQRS.

CDC

CDC, or change data capture, is a way to keep track of row level changes of specific database tables. Often times, it is implemented by reading the database WAL to figure out which rows have been updated, deleted, created, etc. With CDC, it becomes possible to stream changes from a database directly into a queue to be processed by downstream services. With CDC, each change is tracked in a global transaction log. In order to determine at which point in time a CDC consumer should start and end at, LSNs, or log sequence numbers, are used. They tell the database during which time period the client wants to receieve changes for. This allows for CDC events to be replayed, in the event that a client was down and missed CDC events during a specific duration of time. CDC also typically has different modes, either net changes or full changes. Net changes will, over a point in time, give the most recent state of each row which has been changed in the LSN window. Contrarily, full changes will give all the changes which have occurred to a specific row during the selected time. Full changes is especially useful for event streaming, while net changes can be more useful for data warehousing applications

Postgres and CDC

explain postgres specific WAL and config settings, wal deletion, etc

Postgres has extensive CDC support, especially with its configuration options. Traditionally CDC is done by looking at the WAL in order to get a list of actions which the database has performed. The WAL is cleaned up every so often, to maintain speed and performance requirements of the database. Consider the event that a CDC consumer goes down at LSN 10, until LSN 100. If at any point before the consumer comes back up, the database decides to clear the WAL events between 10 and 100, the consumer will actually miss important changes! To combat this, historically the WAL will be written to a separate file, and CDC consumers will have to look to this file in the event the WAL no longer contains the changes they request. But postgres has a more elegant solution. Postres offers what is known as a logical replication slot. This slot keeps track of CDC consumers and what LSN each of them have consumed up to, so it knows what data from the WAL is safe to remove. This ensures that consumers will never miss any data, and the WAL will never be prematurely cleaned up.

Kafka

Kafka is an event streaming platform which stores and streams real time events to consumers. In order to understand the next section, its important to know a couple of key terms

Broker: A kafka broker is essentially a kafka server instance which typically will run only a singular kafka instance Topic: A kafka topic is a named feed or log which consumers will subscribe to, in order to get events which are written to said topic. One topic can have multiple subscribers, and an event is not removed if consumed by a subscriber. It can be thought of as a logical grouping of messages Partition: A kafka partition is a split of a kafka topic. A topic can be split amongst many different servers for reliability or scalability. Event ordering is only guarenteed within a kafka partition, and cannot be guarenteed across multiple partitions in a singular topic. Events can be routed to the same partition by specifying a message key. A partition can be thought of as a the physical grouping of messages on disk. Message Group: A message group in kafka is one or more conusmers which read data from topics. Kafka will manage the message group and evenly distribute the consumers within a message group to read from the underlying partitions of a topic, and rebalance in the event of new or leaving consumers. For example, if there are 6 partitions of a topic, and 3 consumers, kafka will automatically allocated each consumer 2 partitions

Two Postgres Databases

The main point of this experiment, reading the WAL, streaming to kafka, is so that we can have a consumer which reads our kafka topic and writes to a separate postgres database, on an entirely different server. This postgres database instance will be specifically used for reading data. Not only will the server be scalable independently of our write database, but the tables and models within the database will differ completely. This is because we are able to cater directly to what our UI is going to need to display to users, aggregating data across different tables in the write database, utilizing different indexes which might slow down updates or insertions on the write database, etc. This also increases fault tolerance. Read paths of the application will continue to operate if the write db goes down, and vice versa. It also allows for partitioning of data easily, as distributed writes and transactions are much more difficult than distributed reads

What is CQRS?

CQRS, also known as command query response segregation, is a way to separate the models used for writing data and reading data. Within CQRS, a command is a request which updates data, and a query is a request which fetches data. In the context of HTTP, these can be thought of as including, but not exclusive to POST, PATCH, PUT for commands, and GET for queries.

What CQRS is not

CQRS is not the same as DDD. It does not require a separate read database, does not require the use of domain events, eventual consistency, or CDC. At its heart, it is purely concerned with the separation of models for reading and writing, however it enables and is often talked about in the same context as DDD and scalability/performance. Another benefit is code simplicity and separation of concerns, keeping code quality high and repositories organized.

Why CQRS

Although I did explicitly say that CQRS does not require the use of DDD in order to be considered CQRS, in my opinion, the strongest benefit of CQRS comes when utilizing data modeling concepts found in DDD, such as aggregates. An aggregates main purpose is to protect business invariants and ensure that data remains consistent. As such, aggregates often have to encompass many smaller entities in order to protect the rules of the business. Quite often the data required for UI pages does not encompass all of the data in the aggregate, and in some cases could even require data outside the bounds of any one specific aggregate. Because of this, it could become cumbersome to attempt to utilize the aggregate data model to fetch data, especially when no invariants need to be upheld for read operations. Because read operations do not udpate any data and therefore cannot violate any invaraints, SQL queries can be fine tuned and optimized to fetch exactly the data required by the UI without having to worry about upholding business rules. At its most simplest, this can just be implemented with a raw SQL query, selecting and joining any columns from within the same database. This is CQRS at its most pure form, and often times it is enough in order to achieve great separation of concerns and performance increases!

What is this post about?

This post is an excersize taking CQRS to the extreme. Its exhibits a complex, way to encorporate CQRS with a scalable system. It is in no way what should be strived for out of the gate, and is most likely only necessary with extremely hot read paths for thousands of requests a second. Starting with the aformentioned strategy of simply separating DDD aggregate roots for writes and raw sql queries for reads is a great starting point for implementing CQRS.

Data Modeling and Technology

In order to implement this, I used AI (of course at this point), along with some other technologies. Firstly, I want to start with the framework and language, that being NestJS and Typescript.

NestJS actually has an explicit section in the documentation (yes, people still read documentation) for CQRS implementation, meaning the support is great and the implementation is easy to follow. For my implementation, I decided to go with an airline booking service, which would manage flights and seats, and have requirements to fetch some aggregated data for specific flights, such as how many first class seats are left, potential revenue, total price of already booked seats, and more.

@Entity({ name: 'airplanes' })
export class Airplane {
  @PrimaryColumn('uuid')
  readonly id: string;

  @Column({ name: 'tail_number', type: 'text', unique: true })
  readonly tailNumber: string;

  @Column({ type: 'text' })
  readonly model: string;

  @Column({ name: 'base_ticket_price', type: 'numeric', precision: 10, scale: 2, transformer: NumericTransformer })
  private _baseTicketPrice: number;

  @Column({ name: 'status', type: 'text' })
  private _status: AirplaneStatus;

  /** Bumped by the repository on every save; read models expose it as writeVersion. */
  @Column({ type: 'integer', default: 0 })
  version: number;

  @CreateDateColumn({ name: 'created_at', type: 'timestamptz' })
  readonly createdAt: Date;

  @UpdateDateColumn({ name: 'updated_at', type: 'timestamptz' })
  readonly updatedAt: Date;

  /** Always loaded together with the root. Mutate seats through the methods below, not directly. */
  @OneToMany(() => Seat, (seat) => seat.airplane, { cascade: ['insert', 'update'] })
  readonly seats: Seat[];

  /** TypeORM instantiates with no arguments and then assigns columns; the factory passes props. */
  private constructor(props?: { id: string; tailNumber: string; model: string; baseTicketPrice: number; seats: Seat[] }) {
    if (props) {
      this.id = props.id;
      this.tailNumber = props.tailNumber;
      this.model = props.model;
      this._baseTicketPrice = props.baseTicketPrice;
      this._status = AirplaneStatus.ACTIVE;
      this.version = 0;
      this.seats = props.seats;
    }
  }

  static create(input: { tailNumber: string; model: string; baseTicketPrice: number; layout: SeatLayout }): Airplane {
    const { layout } = input;
    const tailNumber = input.tailNumber.trim().toUpperCase();

    if (!/^[A-Z0-9-]{3,10}$/.test(tailNumber)) {
      throw new InvalidAirplaneError('Tail number must be 3-10 alphanumeric characters');
    }
    if (!input.model.trim()) {
      throw new InvalidAirplaneError('Model is required');
    }
    if (!(input.baseTicketPrice > 0)) {
      throw new InvalidAirplaneError('Base ticket price must be positive');
    }
    if (layout.rows < 1 || layout.rows > 60) {
      throw new InvalidAirplaneError('Rows must be between 1 and 60');
    }
    if (layout.seatsPerRow < 1 || layout.seatsPerRow > SEAT_LETTERS.length) {
      throw new InvalidAirplaneError(`Seats per row must be between 1 and ${SEAT_LETTERS.length}`);
    }
    if (layout.firstClassRows < 0 || layout.firstClassRows > layout.rows) {
      throw new InvalidAirplaneError('First class rows must be between 0 and the number of rows');
    }

    const id = randomUUID();
    const seats: Seat[] = [];
    for (let row = 1; row <= layout.rows; row++) {
      const cabin = row <= layout.firstClassRows ? CabinClass.FIRST : CabinClass.ECONOMY;
      for (let i = 0; i < layout.seatsPerRow; i++) {
        seats.push(Seat.create(randomUUID(), id, `${row}${SEAT_LETTERS[i]}`, cabin));
      }
    }

    return new Airplane({
      id,
      tailNumber,
      model: input.model.trim(),
      baseTicketPrice: round2(input.baseTicketPrice),
      seats,
    });
  }

  // ---------- behaviour (commands) ----------

  bookSeat(seatNumber: string, passengerName: string): Seat {
    this.assertActive();
    const seat = this.seatOrThrow(seatNumber);
    const name = passengerName.trim();
    if (!name) {
      throw new InvalidAirplaneError('Passenger name is required');
    }

    const existing = this.seatHeldBy(name);
    if (existing) {
      throw new PassengerAlreadySeatedError(name, existing.seatNumber);
    }

    seat.book(name, new Date());
    return seat;
  }

  cancelSeat(seatNumber: string): Seat {
    const seat = this.seatOrThrow(seatNumber);
    seat.release();
    return seat;
  }

  changeBasePrice(newPrice: number): void {
    if (!(newPrice > 0)) {
      throw new InvalidPriceChangeError('Base ticket price must be positive');
    }
    const ceiling = round2(this._baseTicketPrice * MAX_PRICE_INCREASE_FACTOR);
    if (newPrice > ceiling) {
      throw new InvalidPriceChangeError(
        `Price can be raised to at most ${ceiling.toFixed(2)} in one change (current ${this._baseTicketPrice.toFixed(2)})`,
      );
    }
    this._baseTicketPrice = round2(newPrice);
  }

  ground(): void {
    const booked = this.seats.filter((s) => s.isBooked).length;
    if (booked > 0) {
      throw new AirplaneHasBookingsError(this.tailNumber, booked);
    }
    this._status = AirplaneStatus.GROUNDED;
  }

Taking a look at at the commands themselves, it delegates the business logic to the aggregate root while utilizing a unit of work pattern in order to keep all entity adjustments transactionally consistent 

 
@CommandHandler(CreateAirplaneCommand)
export class CreateAirplaneHandler implements ICommandHandler<CreateAirplaneCommand, CommandResult> {
  constructor(private readonly uow: AirplaneUnitOfWork) {}

  execute(cmd: CreateAirplaneCommand): Promise<CommandResult> {
    return this.uow.create(
      Airplane.create({
        tailNumber: cmd.tailNumber,
        model: cmd.model,
        baseTicketPrice: cmd.baseTicketPrice,
        layout: cmd.layout,
      }),
    );
  }
}

@CommandHandler(BookSeatCommand)
export class BookSeatHandler implements ICommandHandler<BookSeatCommand, CommandResult> {
  constructor(private readonly uow: AirplaneUnitOfWork) {}

  execute(cmd: BookSeatCommand): Promise<CommandResult> {
    return this.uow.mutate(cmd.airplaneId, (airplane) => airplane.bookSeat(cmd.seatNumber, cmd.passengerName));
  }
}

 
@Injectable()
export class AirplaneUnitOfWork {
  private readonly logger = new Logger(AirplaneUnitOfWork.name);

  constructor(
    @InjectDataSource(WRITE_DB) private readonly dataSource: DataSource,
    private readonly airplanes: AirplaneRepository,
  ) {}

  async mutate(airplaneId: string, action: (airplane: Airplane) => void): Promise<CommandResult> {
    return this.dataSource.transaction(async (manager) => {
      // Fail fast instead of queueing forever behind a slow writer.
      await manager.query(`SET LOCAL lock_timeout = '5s'`);

      const airplane = await this.airplanes.findByIdForUpdate(manager, airplaneId);
      action(airplane);
      await this.airplanes.save(manager, airplane);

      this.logger.log(`airplane ${airplane.tailNumber} -> version ${airplane.version}`);
      return { airplaneId: airplane.id, version: airplane.version };
    });
  }

  async create(airplane: Airplane): Promise<CommandResult> {
    return this.dataSource.transaction(async (manager) => {
      await this.airplanes.insert(manager, airplane);
      this.logger.log(`airplane ${airplane.tailNumber} created with ${airplane.seats.length} seats`);
      return { airplaneId: airplane.id, version: airplane.version };
    });
  }
}

CDC

CDC, or change data capture, is a way to keep track of row level changes of specific database tables. Often times, it is implemented by reading the database WAL to figure out which rows have been updated, deleted, or created. With CDC, it becomes possible to stream changes from a database directly into a queue to be processed by downstream services. With CDC enabled, each change is tracked in a global transaction log. In order to determine at which point in time a CDC consumer should start and end at, LSNs, or log sequence numbers, are used. They tell the database during which time period the client wants to receieve changes for. This allows for CDC events to be replayed, in the event that a client was down and missed CDC events during a specific duration of time. CDC also typically has different modes, either net changes or full changes. Net changes will, over a point in time, give the most recent state of each row which has been changed in the LSN window. Contrarily, full changes will give all the changes which have occurred to a specific row during the selected time. Full changes can be especially useful for event streaming, while net changes may be more useful for data warehousing applications

Postgres and CDC

explain postgres specific WAL and config settings, wal deletion, etc

Postgres has extensive CDC support, especially with its configuration options. Traditionally CDC is done by looking at the WAL in order to get a list of actions which the database has performed. The WAL is cleaned up every so often, to maintain speed and performance requirements of the database. Consider the event that a CDC consumer goes down at LSN 10, until LSN 100. If at any point before the consumer comes back up, the database decides to clear the WAL events between 10 and 100, the consumer will actually miss important changes! To combat this, historically the WAL will be written to a separate file, and CDC consumers will have to look to this file in the event the WAL no longer contains the changes they request. But postgres has a more elegant solution. Postres offers what is known as a logical replication slot. This slot keeps track of CDC consumers and what LSN each of them have consumed up to, so it knows what data from the WAL is safe to remove. This ensures that consumers will never miss any data, and the WAL will never be prematurely cleaned up.

Kafka

Kafka is an event streaming platform which stores and streams real time events to consumers. In order to understand the next section, its important to know a couple of key terms

Broker: A kafka broker is essentially a kafka server instance which typically will run only a singular kafka instance Topic: A kafka topic is a named feed or log which consumers will subscribe to, in order to get events which are written to said topic. One topic can have multiple subscribers, and an event is not removed if consumed by a subscriber. It can be thought of as a logical grouping of messages Partition: A kafka partition is a split of a kafka topic. A topic can be split amongst many different servers for reliability or scalability. Event ordering is only guarenteed within a kafka partition, and cannot be guarenteed across multiple partitions in a singular topic. Events can be routed to the same partition by specifying a message key. A partition can be thought of as a the physical grouping of messages on disk. Message Group: A message group in kafka is one or more conusmers which read data from topics. Kafka will manage the message group and evenly distribute the consumers within a message group to read from the underlying partitions of a topic, and rebalance in the event of new or leaving consumers. For example, if there are 6 partitions of a topic, and 3 consumers, kafka will automatically allocated each consumer 2 partitions

Two Postgres Databases

The main point of this experiment, reading the WAL, streaming to kafka, is so that we can have a consumer which reads our kafka topic and writes to a separate postgres database, on an entirely different server. This postgres database instance will be specifically used for reading data. Not only will the server be scalable independently of our write database, but the tables and models within the database will differ completely. This is because we are able to cater directly to what our UI is going to need to display to users, aggregating data across different tables in the write database, utilizing different indexes which might slow down updates or insertions on the write database, etc. This also increases fault tolerance. Read paths of the application will continue to operate if the write db goes down, and vice versa. It also allows for partitioning of data easily, as distributed writes and transactions are much more difficult than distributed reads

Two APIs

To organize this project, there are two main APIs which should be noted. The first, is the API which handles direct HTTP requests from clients, both the command side and read side. The read side will consume from the postgres database and serve the read models which we have created via the debezium + kafka replication process The second API is for consuming the messages from kafka, transforming them, and writing them over to the read datbase. This is also known as a projector, which is when an application is specifically meant to consume data and "project" it into a more consumer-friendly format

Why?

Now with all this complexity, you might be asking why? Well, because I wanted to. But from a professinal standpoint, most of the time something like this wont be necessary. The benefits of CQRS can vastly different depending on how far you want to take it, anywhere from simple code organization to being able to scale each and every part of your application to your specific needs. In this case, the separate read model and read database allow for the read database to be scaled completely separately from the write datbaase, in the event that our system has to serve an absurd amount of read requests per second, but not a lot of write requests.
